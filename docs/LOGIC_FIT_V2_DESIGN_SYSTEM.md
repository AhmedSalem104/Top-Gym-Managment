# Logic Fit Design System V2

**Status:** Canonical UI specification; implementation and migration are tracked separately.  
**Identity:** Original, professional, Vercel/Geist-inspired Logic Fit UI. This is not a pixel copy of another product.  
**Functional rule:** presentation only; existing application behavior remains authoritative.

## 1. Brand foundations

- Primary brand: Azure Blue `#0070F3`. Use semantic tokens, never page-specific copies.
- Preserve semantic success, warning, danger, information, tenant branding and domain-specific visualization colors. Do not mechanically replace every blue hue.
- Arabic: Tajawal. English: Geist Sans. When fonts cannot load, provide language-appropriate sans-serif fallbacks and keep text visible with `font-display: swap`.
- Icon style: Lucide outline geometry, approximately 1.75–2 stroke. One shared icon source and a compact icon subset; do not add per-screen icon libraries or emoji.
- Arabic is RTL; English is LTR. Prefer CSS logical properties; isolate phones, dates, emails, amounts and identifiers as LTR/numeric content.
- Light and Dark are mappings of the same semantic roles and component hierarchy, not separate page designs.

## 2. Token contract

`public/css/tokens.css` is the only canonical source for design values and theme maps. Theme-scoped values in that file are intentional mode mappings, not duplicate owners. Component and feature CSS consumes tokens; it does not redefine global theme values.

Runtime tenant branding remains supported. The default Logic Fit brand is Azure; a tenant's explicitly configured branding must continue to resolve through the existing branding contract.

### Typography

| Token role | V2 target |
|---|---|
| Page title | 24px, weight 600 |
| Main body | 14px, weight 400, line-height 1.6 |
| Secondary | 13px, weight 400 |
| Emphasis | weight 500 |
| Headings | weight 600; line height tuned to heading size |
| Compact data | 12–13px only where density/accessibility permit |

Use tabular figures for aligned numerical columns. Labels remain visible; placeholder is not a label. Print typography has its own semantic mapping while using the same type roles.

### Spacing, shape, elevation and size

- Spacing rhythm: 4px base and 8px primary rhythm; compose section gaps from semantic spacing tokens.
- Buttons radius 8px. Inputs radius 8px. Cards radius 10px. Dialog radius 10px.
- Elevation is restrained: border-first surfaces, low shadows for floating layers only.
- Icon sizes: 16px compact/table, 18px navigation, 20px common button, 24px prominent content.
- Button heights: small 32px, medium 40px, large 44px, prominent 48px; touch targets must still reach 44px when used on touch surfaces. Use the prominent size only for a page's principal scope/action control where the hierarchy warrants it.
- Select a shared z-index scale for content, sticky elements, menus, overlay, modal and toast. Do not resolve stacking bugs by arbitrary per-page z-index escalation.

The member diet-plan and workout-program documents use a dedicated, narrowly scoped cream-and-olive print variant in `public/css/print.css` (`.coaching-plan-print`). Mobile preview stacks the same full-width content without changing its sequence or data.

One primitive has one visual owner. A feature may compose primitives but may not redefine their shared geometry/state. Domain-specific layouts are permitted when they express unique information structure rather than a second visual system.

## 4. Component behavior contracts

- **Buttons:** solid, outline, ghost, soft, destructive and link variants; default, hover, pressed, focus-visible, loading and disabled. Loading preserves width and async semantics.
- **Inputs:** 32/40/44px compact/standard/large controls, persistent label, helper/error association, focus, disabled, readonly and required. Preserve Smart Phone Input parsing and validation.
- **Select/data dropdown:** preserve options, values, keyboard selection, search contracts and dismissal; anchored on desktop and bounded mobile sheet only when a compatible owner can preserve behavior. Action menus are not data selects.
- **Checkbox/radio/switch:** native semantic state and accessible focus; do not create new business toggles.
- **Cards:** 10px radius, 16px standard padding, 12px content gap; headers/footers/dividers are optional compositions.
- **Tables:** header >=44px, rows >=52px, 14px cells, 13px headers, 16px horizontal cell padding. Preserve columns/actions. Record-oriented mobile tables may become cards; comparative/financial data may retain contained scrolling where it protects information integrity.
- **Dialogs/alerts/toasts:** dialogs reuse the canonical `lf-modal-shell` and semantic size/structure variants in `public/css/components/modal-foundation.css`. The approved Modal V3 appearance is an explicit `lf-modal--v3` variant, restricted to MOD-001–MOD-040 in `qa/reports/modal-v3-migration-registry-2026-10-21.md`; it uses token-backed blue-gradient headers, white content and pale-Azure footers. Semantic form/edit/details/confirmation/destructive/selection/structured/large-content/wizard/specialized classes describe purpose without moving business logic into shared UI. The prior `lf-modal--form` chrome remains available for dialogs outside the approved V3 scope until separately approved. Feature modules own content, validation and request lifecycles. Keep the dialog content-sized within viewport bounds; in structured dialogs only the body scrolls, while header/footer remain in flow and do not shrink. Preserve keyboard/focus/Escape and per-dialog dismissal policy. The member-details dialog keeps a viewport-relative frame with its profile header and tab navigation fixed; only the active tab panel scrolls, and selecting a tab returns that panel to its start. Toast position follows locale direction, but delivery queue/timing/dismiss semantics are unchanged unless explicitly approved.
- **Badges:** semantic soft colors, 6px radius and 22/26/30px sizes. Never alter business status meanings.
- **Tabs/segmented controls:** preserve route, selected value, lazy loading and event behavior. Mobile may adapt width/scroll without hiding destinations. Use the canonical `tabs--section-switcher` variant when a small set of peer workspaces sits beside its section heading: the selected destination uses a solid semantic primary surface, while the unselected option remains quiet and legible. In Gym Management, pricing and membership-type catalogs are inline tab panels within the existing management page; the switcher shares the compact section header, and each panel has one concise heading without a repeated modal-style heading. Only create/edit forms remain dialogs. Selecting a panel preserves the current catalog data and CRUD event/API contracts.
- **Backup history:** show non-deleted backup records in the canonical table surface; deleted records are omitted from the visible list while existing deletion/restore/download actions and server audit data remain unchanged. The Owner backup-history screen presents the backup table without the separate audit-log table. Keep the table wrapper border visible in both themes and use the shared table header, row, and responsive-card behavior.
- **Gym Dashboard views:** the Dashboard page may use the canonical inset-surface tab variant for local views. Its default Overview view contains the existing overview cards, alerts and daily passes; Analytics remains a separate owner-authorized view. These local tabs must not alter the global page-navigation routes or permission checks.
- **Navigation:** preserve item inventory, routes, permission visibility, group membership semantics, branch context and deep links. At desktop widths the topbar occupies only the content column beside the directional sidebar; the sidebar surface fills its column from the top edge through the full workspace/page height, while navigation items begin below the topbar (256px from 1280px, 224px from 1024px, with a 72px collapsed rail). The navigation rail itself remains sticky and viewport-height with its own overflow for long navigation lists. Tablet and phone widths use the existing accessible viewport-height navigation drawer and full-width topbar; its drawer control is the sole Navbar navigation shortcut. The desktop application-grid launcher is intentionally omitted because the persistent sidebar already exposes the same permitted routes. The sidebar pin action remains available as an icon-only control with a localized accessible name and tooltip. The existing logout action stays in the sidebar and uses the canonical destructive button variant in both themes. Branch/section context controls are not rendered in the Navbar; the Dashboard's data-scope bar is the visible entry point and stages authorized branch/section options in its existing dialog. The existing in-memory selects remain mounted as the context-state backing store, retaining session scope, events, authorization and handlers. User identity is read-only and sourced from the authenticated session. The More menu contains the locale selector, theme, fullscreen and existing contextual actions. The locale selector is a compact 46px two-choice control with Arabic on the left and English on the right; the active choice uses a quiet white/theme surface, thin locale-accent outline and matching text, while both choices retain localized accessible names. All controls retain their existing handlers and permission checks.
- **Operational intelligence workspace:** the existing insights, retention table, assistant query, and plan builder are organized into three equal-size accessible local tabs (Overview, Assistant, Plans). Tabs preserve the same DOM-backed forms, data nodes, permissions, and action handlers; selecting a tab only changes which existing content panel is visible. The plan-type choice inside the Plans panel uses the canonical section-switcher tab treatment as a distinct, full-width group with localized labels and explicit tab-to-panel relationships; selection continues to show the existing workout or nutrition fields without changing plan behavior.

## 5. Responsive and accessibility rules

QA targets: 320, 375, 390, 430, 768, 1024, 1280, 1440 and 1920px. The shell uses a 64px desktop/tablet topbar and 56px phone topbar; content gutters are 24px from 1280px, 16px from 768px, and 12px below 768px. Gym Dashboard overview cards use four equal columns from 1280px, two columns from 360px to 1279px, and one column below 360px. The expected layout is intentionally adapted at each width; never merely scale desktop. No unintended page overflow, clipped actions/menus, hidden permission-gated controls or unreadable financial values.

All controls need keyboard operation, visible focus, semantic names/roles/states and touch-sized targets. Contrast target is WCAG AA for normal text; state meaning cannot rely on color alone. Respect `prefers-reduced-motion`, safe areas and browser zoom. Visual and accessibility acceptance must be evidenced in the browser, not inferred from CSS declarations.

## 6. Localization

- Dynamic Coaching builder headings, wizard steps, progress counts, action hints and field labels use the central Arabic/English catalog. Localizing option labels must preserve their original domain values explicitly; translation changes presentation only. Locale switches while the builder is open refresh its visible labels without reloading data or changing the draft.

New/modified user-facing text has Arabic and English presentation. Machine values, enum codes, API payloads, routes and business identifiers are not translated. Locale-specific formatting may affect presentation only. Do not change account/session persistence to store a locale without an approved contract. For now, use the existing in-memory/page locale source and keep any new persistence decision separate.

## 7. Legacy migration and cleanup

No legacy file is removed by filename or age alone. Map selectors to HTML/JS consumers and generated outputs, migrate each consumer to canonical V2 owners, run functional and visual checks, then delete only proven-dead visual rules. Keep necessary print/domain CSS and behavioral classes. Never edit `main.css` or other generated files by hand; use the existing build pipeline and review resulting artifacts.

The former `visual-redesign.css` layer was retired on 2026-10-11 after its remaining rules were reconciled with canonical owners and targeted unit/browser verification passed. Do not recreate that file or another parallel global layer. Continue the same consumer-mapping, migration, and verification process for any other legacy stylesheet before removing it. No `fix.css`, `overrides.css`, or new global layer is permitted.

## 8. Evidence required for screen acceptance

For each real route/view and role-dependent composition, record before/after screenshots, tested locale, theme, viewport, relevant states, preserved actions/contracts and test command/results. Print acceptance additionally requires actual rendered PDF/print preview inspection for existing formats and short/long content. Use a deliberate compact document rhythm: avoid oversized page insets, repeated section gaps, and blank media blocks while preserving legible type, real-image dimensions, section hierarchy, and page-break integrity. Missing-image placeholders should be visibly neutral but materially shorter than loaded report imagery. Mark unrun or inaccessible cases honestly; do not infer coverage from a static inventory.
