The tables above record the accepted state values and the user/system transitions exposed by current services. They intentionally do not invent a complete Cartesian graph of every possible state pair. Where a status endpoint accepts a value but the product has no explicit transition rule, the mobile contract is “invoke only a currently surfaced action, then re-fetch server state”; this is documented behavior, not an unmapped flow.

## State synchronization rules for clients

1. Fetch state after mutation and treat server response as authoritative.
2. Never equate an HTTP success toast with a later email delivery or notification read state.
3. On `409`, reload the aggregate and render its current state; do not repeat a terminal transition.
4. Calculated states (membership expiry/freeze, plan access, unread count) must not be persisted or authorized from a client calculation.
5. Do not infer unexposed transitions from enum values for member requests, day passes, Trainer package/task, stock transfers, or Platform lifecycle. Their current operations and state guards are mapped above; an additional transition requires an explicit product/API contract.

## Additional status facts verified in services

- Membership UI/service status can be computed as `active`, `expiring_soon`, `expired`, `frozen`, or `cancelled`; these are not guaranteed to be one persisted membership `status` column. Freeze is represented by a separate freeze record and affects effective end date/access.
- Attendance is represented by a daily event/open visit; duplicate same-day check-in is rejected with conflict, and checkout requires an eligible open event. Automatic checkout is a system transition after configured policy, not a mobile action.
- Trainer session UI exposes `scheduled`, `completed`, `cancelled`, and `no_show`; only the transitions accepted by `/api/trainer/sessions/:id/status` are actionable. A user-visible label does not prove all states can be assigned directly.
- Tenant/subscription/plan accepted states and scheduled-change semantics are detailed in the Platform lifecycle table below; use exact action endpoint and server response rather than locally composing a transition.

| Aggregate | Stored/accepted values | Supported transition semantics |
|---|---|---|
| Tenant | `trial`, `active`, `suspended`, `expired`, `archived` | Platform lifecycle endpoints accept supported next status with reason where required; do not assume every pair is valid or forbid a pair unless that action/service says so. Expiry reconciliation can set `expired`. |

|---|---|---|---|---|---|

| Unread notification | Mark read/read all → addressed recipient | Staff `notifications.read` or Portal endpoint's session identity; recipient and tenant resolved server-side | `/api/notifications/:id/read`, `/read-all`; portal-specific read route | Per-user read state changes; unread count updates | Foreign ID is not revealed; session/permission/tenant mismatch. |

Payments are not one universal mutable status machine. Gym collection/refund history is append-only financial evidence; subscription snapshots do not create a second cash event, and refunds are explicit adjustments. Trainer package purchases have `cancelled`/`expired` guards; consuming the last package session transitions purchase to `completed`. Do not invent generic `paid → refunded` rewriting semantics.

## Portal identity/session lifecycle caveats

Gym-member and Trainer-client portals have separate server-resolved identity modes even when they share the Portal page. Portal session creation stores a hashed session token and uses an HttpOnly/SameSite cookie (Secure in Production); duration is configurable from one to seven days, default one day. Resolver checks the session's own revocation flag and expiry; no portal logout/revoke route or current issuer of portal-session revocations was found. Membership-code revocation/rotation blocks new lookup only and does not revoke an existing session; no code-expiry predicate was found. Lookup checks tenant `trial`/`active`, but existing session resolution does not re-check tenant status. Whether tenant suspension, code rotation, or Trainer client pause/archive should invalidate existing sessions is recorded as Product/Security decisions in 21. The current Web reload begins at code entry; the native session endpoint returns only tenant/member identity, then the client loads data separately.
