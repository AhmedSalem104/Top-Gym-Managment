# 23 — Web-to-Mobile Functional Parity Audit

Audit date: 2026-10-01
Authority: executable Web/Backend source in this repository. This document is a discovery/traceability artifact, not a mobile implementation plan approval.

## Scope and evidence

Inspected the current route registration and route modules under `src/routes/`, controller/service ownership, permission and feature catalogs, `public/index.html`, Gym page modules under `public/js/pages/`, the shared Gym shell/action wiring in `public/js/app.js` and `public/js/auth-ui.js`, Trainer Studio runtime, Member Portal runtime, Platform Admin runtime, and the existing Mobile Blueprint/API/test references.

The API catalog declares 351 method/path registrations in 29 route modules. It is the route-level index; field-level payloads remain distributed across route/controller/service/tests and there is no checked-in machine-readable OpenAPI schema. The Gym shell exposes 17 `data-page-tab` destinations in `public/index.html`; additional hidden/direct panels and dashboard entry points exist. Runtime-generated controls and permission/entitlement-conditioned actions mean HTML-only control counts would be misleading. The native/mobile application source is not present in this Web/Backend repository; mobile implementation status therefore cannot be verified from this repository.

The repository's existing `npm run qa:screen-inventory` scanner was also run. Its current static counts are: 13 HTML entry pages; 19 active Gym hash views (including the separately routed surfaces represented by view hooks); 9 Platform Admin panels; 6 registration steps; 6 Member Portal roots; 9 Store subviews; 5 Portal tools; 20 nested view/step hooks; 29 identified overlay roots; 193 form/filter-related element hooks; and 68 state-related element hooks. These are independent/overlapping hook counts, not additive unique-screen or action counts. The complete generated element-ID lists are in [`../COMPLETE-SCREEN-INVENTORY.md`](../COMPLETE-SCREEN-INVENTORY.md). The scanner's `STRUCTURAL QA PASS` means the current structural report matches its discovered hooks; it does not establish field/API/action completeness.

Coverage terms in this audit:

- `COVERED`: the Blueprint states the capability/flow/API boundary at the granularity evidenced here.
- `MISSING_FROM_BLUEPRINT`: source-visible item/action/state is not represented at that granularity in the prior Blueprint; this audit now records it below.
- `DOCUMENTED_NOT_IMPLEMENTED`: Blueprint destination/contract exists, but this repository provides no mobile implementation evidence.
- `IMPLEMENTED`: executable mobile source/test evidence is available in the audited repository. None is asserted by this audit.
- `MOBILE_NOT_APPLICABLE`: intentionally excluded with the security/operational reason recorded below.
- `NOT_VERIFIED`: evidence is unavailable; this is not a pass state.

### Exact dashboard content atoms found in source

`public/index.html` and `public/js/pages/dashboard/analytics.js` establish the following dashboard atoms (a card may contain multiple atoms):

- Hero: Logic Fit/tenant brand and subtitle; current plan; current member total; subscription **start date** (runtime reads `startsAt`/`startDate`); live/system copy; member-list link; Owner-only subscription/plan print and price print-preview actions.
- Member overview: total members; active memberships; memberships expiring within seven days; expired memberships; currently frozen memberships.
- Daily alerts: count, local search by member name/phone, results list, phone link, WhatsApp link. No direct detail/renew action is rendered by the inspected alert binding.
- Monthly finance snapshot: subscription collections, expenses, net, and link to the Expenses screen; the expense list/add action is owned by that screen, not Dashboard.
- Day passes: month count/revenue summary and Add/Manage actions; list table and row actions are in the Day Pass screen.
- Store summary: markup and optional API payload exist, but runtime always hides the summary container; it is not a visible Dashboard element.
- Owner analytics period tabs: week/month/year. Smart strip: health score/label, active rate/count, expense ratio, net-positive/negative insight, and prioritized outstanding/expiring/inactive-member insight.
- Analytics KPI cards: new members; collected amount and paid transaction count; net; attendance visits and unique members; outstanding amount/count; attention count derived from expiring+expired and inactive-member count.
- Analytics charts/series: collections vs expenses trend; member status distribution; subscription distribution; payment-method distribution; member/subscription activity; attendance peak-time distribution; most-attending members; members absent seven days.
- Dashboard runtime states: initial skeleton; analytics loading/refresh; no-chart-data; API error/partial region state; permission-hidden financial/Owner regions; empty day-pass list. Expenses and Store empty states belong to their own screens. The service/API response is authoritative for all values and scopes.

No distinct notification feed widget was found in the dashboard body inventory: the shared shell notification center is separately rendered by `public/js/notification-center.js`. Dashboard “branch/section selector” is not a dashboard-local widget; branch context is owned by the shared branch context/shell. This distinction prevents claiming a dashboard component that is not present.

Alert WhatsApp is a two-step external side effect: `GET /api/members/:id` supplies the contact snapshot, then `POST /api/members/:id/alert-communications` records an `opened` or `sent` event before opening/sending through WhatsApp. The recorded `opened` state is not proof of message delivery. This is guarded by `members.read` and `members.alerts`; a `403`/scoped `404` or external-app handoff failure must not be described as a successful send.

## API route registration disposition

The 351 declarations in `03-API-CATALOG.md` are the full registered API denominator, including compatibility routes and public/health routes. In particular, presence of a route in a UI-owning module does not prove that every sibling route in that module is called from UI.

Actionable API crosswalk source evidence:
