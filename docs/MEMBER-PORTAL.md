# بوابة المشترك

## النطاق

بوابة المشترك تسمح لصاحب العضوية بعرض بياناته باستخدام كود عشوائي مستقل عن رقم العضو والاشتراك والإيصال وQR الحضور. كل عملية عرض تُبنى كتقرير لمشترك واحد فقط؛ لا يتم تحميل قائمة أعضاء أو دمج سجلات بين المشتركين.

## الكود

- يُنشأ تلقائيًا داخل Transaction إنشاء المشترك.
- يتم توليد أكواد للمشتركين الحاليين عند أول تشغيل لمسار العضوية بعد الترحيل.
- الكود العشوائي بصيغة `TG-XXXX-XXXX-XXXX-XXXX`، ويظل ثابتًا عند التجديد.
- قاعدة البيانات تحفظ HMAC للكود للتحقق ونسخة AES-256-GCM مشفرة لاسترجاعه من Owner عند الإرسال أو العرض.
- إعادة الإصدار تستبدل الـHash والنسخة المشفرة، ولذلك يتوقف الكود القديم فورًا.
- لا يُكتب الكود الكامل في Logs أو Audit؛ يسجل Audit العملية والعضو والمستخدم والوقت وبيانات الطلب غير الحساسة.

## قاعدة البيانات

تضاف إلى `dbo.members` الأعمدة:

| العمود | الغرض |
| --- | --- |
| `membership_code_hash` | HMAC-SHA-256 للتحقق من الكود بدون تخزينه كنص |
| `membership_code_ciphertext` | نسخة AES-256-GCM مشفرة لاستخدام Owner |
| `membership_code_version` | إصدار الكود وإبطال الإصدارات القديمة |
| `membership_code_issued_at` | وقت الإصدار الحالي |
| `membership_code_revoked_at` | حالة الإلغاء |

وسجل العمليات في `dbo.gym_membership_code_audit` للأحداث: `issued`, `viewed`, `whatsapp_sent`, `rotated`, `portal_viewed`.

التشغيل العادي يضمن الأعمدة والجداول بطريقة idempotent عبر `ensureMembershipCodeStorage()`، كما أن `database/schema.sql` يحتوي على نفس Migration للتثبيت الكامل.

## API

### حالة ازدحام الجيم

`POST /api/member-portal/occupancy`

Body:

```json
{ "membershipCode": "TG-ABCD-EFGH-JKLM-NPQR" }
```

يعيد المسار قراءة مجمعة صغيرة فقط:

```json
{
  "presentCount": 4,
  "level": "quiet",
  "label": "هادئ",
  "staleCheckInsExcluded": 0,
  "observedAt": "2026-08-30T12:00:00.000Z",
  "refreshAfterSeconds": 30
}
```

يتم حل مالك الكود أولًا ثم تنفيذ القراءة داخل `tenant_id` الخاص بالجيم. لا يعيد المسار أسماء أو معرفات أعضاء، ولا ينفذ تسجيل انصراف تلقائيًا أو أي تهيئة/كتابة. السجلات المفتوحة الأقدم من مدة `ATTENDANCE_AUTO_CHECKOUT_MINUTES` تستبعد منطقيًا من العد، مع إرجاع عددها فقط للتوضيح.

يمكن ضبط حدود التصنيف من البيئة:

```text
MEMBER_PORTAL_OCCUPANCY_MODERATE_AT=6
MEMBER_PORTAL_OCCUPANCY_BUSY_AT=16
MEMBER_PORTAL_OCCUPANCY_VERY_BUSY_AT=31
```

بعد نجاح lookup، تعرض البوابة الحالة وتحدّثها كل 30 ثانية أثناء بقاء الصفحة ظاهرة، وتتوقف مؤقتًا عند إخفاء التبويب لتقليل الطلبات.

### عامة

`POST /api/member-portal/lookup`

Body:

```json
{ "membershipCode": "TG-ABCD-EFGH-JKLM-NPQR" }
```

لا يعيد المسار الكود ولا الملاحظات الإدارية. يعيد بيانات العضوية والاشتراكات والمدفوعات والحضور والتجميد الآمنة للعرض.

يحل الخادم مالك الكود أولًا عبر HMAC محدد، ثم يعيد قراءة بيانات المشترك داخل سياق `tenant_id` الخاص بالجيم نفسه مع استمرار SQL Server RLS. لذلك لا يعتمد portal على `DEFAULT_TENANT_SLUG=top-gym` لقراءة أعضاء الجيمات الأخرى. يمكن تمرير `?tenant=<slug>` في الرابط لتثبيت هوية الجيم، وتضيف الروابط الإدارية المولدة هذا المعامل تلقائيًا، مع بقاء الرابط العام المختصر متوافقًا لأن الكود نفسه يحدد الجيم بأمان.

### Owner

| المسار | الوظيفة |
| --- | --- |
| `GET /api/members/:id/membership-code` | حالة ونسخة مختصرة فقط |
| `POST /api/members/:id/membership-code/reveal` | عرض الكود الكامل مع Audit `viewed` |
| `POST /api/members/:id/membership-code/resend` | استرجاع نفس الكود مع Audit `whatsapp_sent` |
| `POST /api/members/:id/membership-code/rotate` | إلغاء القديم وإصدار كود جديد |

كل المسارات الإدارية محمية بجلسة النظام و`Owner`، ولا يُقبل الكود العام داخل URL.

## تقييم التجربة

بعد نجاح الدخول تظهر في البوابة استمارة `قيّم تجربتك` من خمس نجوم، مع نوع
الملاحظة (`general`, `problem`, `complaint`, `suggestion`، أو
`feature_request`) ونص يصل إلى 4000 حرف. يبقى كود العضوية في ذاكرة الصفحة فقط
بعد نجاح lookup، ويُرسل إلى `POST /api/member-portal/feedback` للتحقق منه ثم
ربطه بـ`member_id`.

تخزن SQL Server التقييم والنوع والنص ووقت الإرسال ومعرّف العضو فقط في
`dbo.gym_member_feedback`; لا يخزن الجدول كود العضوية. وتُنفذ عملية الإدخال داخل
سياق الجيم الذي يملكه الكود، حتى لا يُكتب تقييم مشترك في Tenant آخر. نقطة الإرسال
عامة من أجل البوابة، لكنها محمية بمحدد محاولات مستقل حسب IP وبصمة الكود.

## شاشة Owner

يظهر تبويب `#feedback` للـOwner فقط. تعرض الشاشة اسم العضو ورقم الهاتف والنجوم
ونوع الملاحظة والنص وتاريخ الإرسال، مع فلاتر التقييم والنوع والتاريخ والبحث
والترقيم. زر `تفاصيل العضو` يعيد استخدام مسار تفاصيل العضو الإداري الحالي.

لا يملك Assistant تبويب الشاشة، كما أن `GET /api/member-feedback` يرفضه
الـBackend بـ`403` حتى عند طلبه مباشرة.

## واتساب

رسالة الترحيب الحالية تحتفظ بنفس Flow، ويضاف إليها الكود ورابط `/member-portal` عندما يرسل المستخدم رسالة الترحيب. من تفاصيل العضو يمكن طلب إعادة الإرسال للكود نفسه.

## الطباعة وPDF

زرَا `طباعة التقرير` و`تنزيل PDF` يفتحان نافذة الطباعة القياسية للمتصفح مع CSS A4؛ يختار المستخدم Save as PDF من حوار الطباعة. التقرير لا يعرض كود الدخول الكامل ولا الملاحظات الإدارية، ويحتوي على رقم التقرير والتاريخ والسجلات والتوقيعات.

## متغيرات البيئة

يفضل ضبط:

```text
MEMBERSHIP_CODE_SECRET=<long random secret>
PUBLIC_APP_URL=https://your-production-domain.example
```

إذا لم يُضبط `MEMBERSHIP_CODE_SECRET`، يستخدم النظام مصدرًا سريًا ثابتًا متاحًا في الإعدادات الحالية للحفاظ على التوافق، لكن يظل ضبط المتغير الصريح هو الإعداد الموصى به للإنتاج.

## الاختبار الأمني

- توجد Rate Limit مستقلة لمسار البحث العام حسب IP وبصمة أحادية الاتجاه للكود.
- الخطأ العام لا يوضح هل العضو موجود.
- لا يعاد أي كود من صفحة البوابة.
- لا تصل البوابة إلى عضو آخر لأن البحث يتم على HMAC للكود فقط.
- لا تتغير جداول QR والحضور ولا طريقة عملها.
